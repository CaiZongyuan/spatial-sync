## Problem Statement

当前平台虽然已经具备 `Asset Library`、`Scene Library`、统一动作管线以及策略评估与晋升的骨架，但真正在仿真中运行的机器人和实验设备全部依赖手写轨迹插值或状态机脚本，尚未跑通任何一台由强化学习 `Policy` 实时闭环驱动的 `Embodiment`。当开发者希望将外部开源机器人（如双足 Microduck）或后续自行建模搭建的新具身 `Asset`（双足、四足、轮臂、自定义多关节机构）引入平台开展训练与仿真时，面临三道结构性断层：

第一，**具身 `Asset` 到本地训练引擎的通用管道缺失**。现有训练调度仅预留了重量级 Omniverse/PhysX 命令行入口，既与本平台默认使用的 MuJoCo Warp 物理求解器存在跨引擎接触代沟，又难以在单张工作站显卡上轻快地将任意标准 USD 关节机器人 `Asset` 组装为高吞吐并行强化学习训练环境。

第二，**观测、控制、评估与场景定位概念被固定底座单动作机械臂锁死**。仿真物理端口缺少移动与动态平衡具身必需的本体角速度（陀螺仪）读取；观测与动作契约缺少机体坐标系重力投影、有界动作指令向量输入以及围绕默认站姿偏移的关节目标位置空间；策略评估准入硬编码只接受单一机械臂 `EntityType`；设备程序一次只能挂载单个 `Policy` 且将动作参数死绑在固定地点名上；场景中也只有面向固定底座关节角的 `Teach Location`，缺少面向移动机器人的地面目标 `Waypoint`。这导致任何移动机器人或多动作自定义具身都无法进入平台的评估、晋升与跨场景操作体系。

第三，**缺乏端到端已验证的具身智能标杆与清晰的分层边界**。用户与 `Agent` 需要一套既能在日常会话中像操作普通设备一样通过声明式动作驱动机器人跨场景作业（`Agent` 负责高层规划，`Policy` 负责高频全身平衡控制），又能在 `RSI loop` 中由 `Agent` 担任科研教练持续改进 `Controller` 的真实闭环样板，而非为某一款特定机器人编写一次性特判脚本。

## Solution

构建一套**平台核心层零特定机器人硬编码**的通用具身训练、评估与跨场景运行基础设施，并用双足 **Microduck** 完成首次端到端标杆落地：

1. **通用本地并行训练后端**：在计算节点新增与平台 `NewtonSimulation`（MuJoCo Warp 求解器）物理同源的轻量 Linux 原生 **MuJoCo Warp（`mjlab` + `rsl_rl` PPO）** 训练后端（[ADR-0006](../adr/0006-mujoco-warp-training-backend.md)），复用平台统一的 `Task`、`Training Plan`、`Approval Gate`、`Job` 心跳、指标流与 ONNX 导出契约。以平台规范的 `Z-up` USD `Asset` 为唯一物理事实源确定性派生训练表示，支持任意合规多关节机器人 `Asset` 通过声明式任务定义直接在单张本地 GPU 上完成高吞吐并行训练，无需引入特定硬件的私有电机电路或串联齿隙外挂（[ADR-0007](../adr/0007-standard-usd-joint-drives-for-simulated-embodiments.md)）。
2. **面向任意具身的感知、动作与评估泛化**：在仿真物理端口补齐刚体线速度与角速度读取；在 `ObservationSpec` 中扩展机体角速度、机体坐标系重力投影、有界动作指令向量（服务速度跟踪、姿态俯仰参数等多类含参动作）与基于默认姿态偏移的关节位置动作空间；解除策略评估与晋升对单一机械臂接口的限制，使任何声明式机器人 `EntityType` 都能走通从 `Job` 产物入库、`Evaluation Suite` 固定可比较条件自动考评到 `Controller` 晋升的全链路。
3. **多动作策略调度与跨场景 `Waypoint` 导航**：在领域模型与 `Scene` 规范中引入地面目标 **`Waypoint`（路点）**（与固定底座关节角 `Teach Location` 明确区分）。提供通用的多策略 `Device Program` 机制，将 `EntityType` 的各个声明式动作（如行走、倒地恢复、互动致意）映射到各自训练产出的 `Policy`（[ADR-0008](../adr/0008-multi-policy-dispatch-and-velocity-guided-waypoint-locomotion.md)）；移动导航采用工业界标准的“外层 `Waypoint` 速度导引 + 内层高频速度跟踪 `Policy`”分层架构，使同一套训练好的运动 `Policy` 无需重训即可放入任意 `Scene` 包走向任意新 `Waypoint`。
4. **双足 Microduck 标杆闭环与开箱演示**：基于上述通用底座（核心层不含任何 Microduck 专属分支），导入标准 `Z-up` USD 机器人 `Asset`（保留上游 Apache-2.0 溯源），注册双足 `EntityType`、`Embodiment`、`Robot Model` 与 `Controller`，建立标准训练评估场及跨场景巡检演示场景，在本机 GPU 上真实训练并通过平台 `Evaluation` 合格入库首批 3 个代表性声明式动作 **`walkTo`（定向巡检行走）**、**`standUp`（跌倒自主起身）** 与 **`bow`（鞠躬致意互动）** 作为初始 `Reference` 随库交付，实现一条命令启动即可在浏览器、CLI 与 MCP 中操控与复训。

## User Stories

### 通用自建与导入具身资产接入
1. 作为具身资产构建者，我希望将自己建模或从外部转换的标准 `Z-up` USD 多关节机器人导入 `Asset Library`，以便无需修改平台底层代码即可将其用于仿真与强化学习训练。
2. 作为具身资产构建者，我希望机器人 `Asset` 携带完整的 `Binding Template`（声明其实现的 `EntityType`、受控关节、躯干刚体与关键站点角色），以便将该机器人放入任意新 `Scene` 时自动生成有效设备绑定。
3. 作为具身资产构建者，我希望平台使用统一的 `UsdPhysics` 标准关节目标位置与目标速度通道驱动机器人，以便纯仿真阶段的训练环境与平台运行时保持一致的物理响应，而不耦合特定真机硬件的私有电机插件。
4. 作为具身资产构建者，我希望平台自动校验机器人 `Asset` 的关节限位、质量惯量、碰撞体与物理时钟合法性并生成 `Validation Report`，以便在启动训练前拦截结构或物理缺陷。
5. 作为平台开发者，我希望新增自定义机器人 `EntityType` 时静态场景预览能够准确感知设备类型集合变化并完成刷新校验，以便不会出现过期预览被误判可用的情况。

### 跨场景布局与 `Waypoint` 导航
6. 作为场景构建者，我希望在任意 `Scene`（标准测试场、实验室场景或自定义房间场景）中定义命名的地面 `Waypoint`（包含地面位置与期望朝向），以便移动机器人在不依赖关节示教角的情况下获知巡检或驻留目标。
7. 作为场景构建者，我希望系统清晰区分固定底座机械臂使用的 `Teach Location` 与移动机器人使用的 `Waypoint`，以便两类机器人在同一 `Scene` 中共存协作而不混淆语义。
8. 作为场景构建者，我希望将同一个机器人 `Asset` 放入不同的 `Scene Version` 中并直接复用其已晋升的运动 `Policy`，以便换房间或调整布局时无需重新训练底层步态。

### 本地单卡并行强化学习训练（MuJoCo Warp 后端）
9. 作为算法训练者，我希望在计算节点上使用轻量 Linux 原生的 MuJoCo Warp + `rsl_rl` PPO 训练后端运行 `Task`，以便在单张工作站 GPU 上几分钟内完成高动态具身策略训练，且无需跨系统拉起重量级图形引擎。
10. 作为算法训练者，我希望训练后端从锁定的规范 USD `Asset` 与 `Scene Version` 确定性派生求解器模型，以便训练时的连杆惯量、关节顺序、默认站姿和驱动刚度阻尼与平台 `NewtonSimulation` 严格对齐，最小化跨环境物理代沟。
11. 作为算法训练者，我希望为任意自定义或导入机器人编写声明式 `Task`（指定目标 `Scene Version`、目标机器人实体、所实现的 `EntityType` 动作、观测规格、奖励项、随机化范围与成功判据），以便用统一格式扩展新动作和新机器人。
12. 作为算法训练者，我希望通过平台标准的 `Training Plan` 提交训练轮次并经过人类 `Approval Gate` 审批 GPU 预算后才派发 `Job`，以便所有算力消耗与实验意图受控可追溯。
13. 作为算法训练者，我希望在训练运行期间通过平台实时查看计算节点心跳、GPU 状态、TensorBoard 训练曲线与日志，并在取消或异常退出时由节点可靠回收整个训练进程树，以便安全管理长时训练作业。
14. 作为算法训练者，我希望训练 `Job` 结束后自动导出包含观测归一化参数、符合平台 `ObservationSpec` 与输入输出维度契约的纯前向 `.onnx` 模型及溯源摘要，以便无缝衔接平台 CPU 确定性推理与评估。

### 通用具身观测、多动作控制与运行态交互
15. 作为策略运行时消费者，我希望仿真物理端口提供刚体在世界或机体坐标系下的角速度以及重力方向在机体坐标系的投影，以便双足、四足等欠驱动机器人获得维持动态平衡所必需的本体前庭感知。
16. 作为策略运行时消费者，我希望 `ObservationSpec` 支持有界动作指令向量（如期望速度或目标俯仰参数）以及基于默认姿态偏移的关节目标位置动作空间，以便覆盖足式与移动具身的标准控制范式。
17. 作为机器人 `Device Program` 作者，我希望同一个机器人实体的程序能够按动作名同时挂载多个已注册 `Policy`（例如行走、起身、鞠躬分别对应各自的 `Policy`），以便用户和 `Agent` 直接调用声明式动作即可触发对应行为，而无需手动切换策略槽位。
18. 作为实验室操作 `Agent`，我希望通过统一的 HTTP 动作管线（CLI 或 MCP）向移动机器人发送高层动作指令（如前往指定 `Waypoint`、跌倒起身、鞠躬致意、紧急停止），以便专注于高层任务规划（大脑），将高频全身平衡控制交给底层 `Policy`（小脑）。
19. 作为 Web 用户，我希望在浏览器三维视口中实时观看机器人在不同场景中迈步走向目标 `Waypoint`、跌倒后自主爬起以及执行互动动作，并能直接点击设备控制面板触发或中止动作，以便直观检验训练成果。
20. 作为操作者，我希望当机器人在行走途中发生意外倾覆超限、目标 `Waypoint` 不存在或超时未到达时，动作管线返回结构化失败码并更新设备状态属性（如跌倒状态、当前所在 `Waypoint`、运行阶段），以便 `Agent` 能够据此决策调用起身恢复动作。

### 具身评估、晋升与 RSI 自我改进闭环
21. 作为评估负责人，我希望策略评估系统支持任意机器人 `EntityType`（不限于机械臂），在锁定可比较条件的 `Evaluation Suite` 场景版本中运行多回合确定性 `NewtonSimulation` 并按 `Task` 成功条件自动打分录制，以便客观衡量任何新具身候选策略。
22. 作为评估负责人，我希望移动机器人的动作参数覆盖校验基于连续指令或距离包络而非死绑单一地点名，以便策略既能在训练评估集上安全校验边界，又能合法泛化到新场景的 `Waypoint`。
23. 作为具身 `RSI loop` 的优化 `Agent`，我希望读取 `Lab Notebook` 中历次 `Hypothesis` 的评估得分与失败录像，提出调整奖励权重、观测或控制参数的新 `Training Plan`，以便系统化迭代提升 `Controller` 表现。
24. 作为人类审批者，我希望首个 `Reference` 由我在 `Approval Gate` 批准建立基线，且后续 `Candidate` 必须满足既有置信下界改进与私密测试集规则并经我审批后才晋升为对应 `Controller` 的新 `Reference` 版本，以便守住默认运行质量。

### 双足 Microduck 首航标杆验收
25. 作为新加入项目的开发者，我希望开箱即获得完整的双足 Microduck 标杆套件（规范 USD `Asset`、双足 `EntityType`、`Embodiment`、`Robot Model`、标准训练场、跨场景巡检示例场景以及实训合格的 `walkTo`、`standUp`、`bow` 三个初始 `Reference` `Policy`），以便一条本地命令就能在浏览器中看到真实策略驱动的双足机器人，并以此为模板开发我自己的下一个具身机器人。

## Implementation Decisions

### 1. 通用化红线（平台核心层零特定机器人硬编码）
- 物理仿真运行时、策略推理与观测拼装、策略资格审查与评估器、训练作业协议以及计算节点 MuJoCo Warp 训练桥接器，**一律面向抽象的关节/刚体/站点与声明式配置编程，严禁出现任何针对 Microduck 或特定机器人名称的条件分支**。
- Microduck 完全以标准用户态内容包的形式存在（一个 `robot` 类 `Asset`、一个通用双足 `EntityType`、一组 `Scene Version`、一组 `Task` 与训练产出的 `Policy` / `Controller`）。后续新增四足、轮臂或自建异形机构时，无需改动平台核心模块。

### 2. 物理资产与驱动边界（遵循 ADR-0001、ADR-0003、ADR-0006、ADR-0007）
- **规范格式与坐标约定**：所有自建与导入具身 `Asset` 保持 `Z-up`、右手系与 USD（`UsdPhysics`）唯一事实源；浏览器渲染网格与 MuJoCo Warp 训练求解器表示均由锁定的规范 USD 资产确定性派生，保留完整的上游来源与开源许可证声明。
- **标准关节驱动**：物理端口保留关节目标位置（`joint_target_q`）与关节目标速度（`joint_target_qd`）两个标准提交通道；策略动作空间 `joint_position_offset` 计算出的目标位置在固定控制节拍（如 50Hz）下写入 `joint_target_q`（`joint_target_qd` 默认置零，或仅由外层程序在急停/阻尼阶段显式设置），由底层求解器按关节刚度、阻尼、电枢惯量与摩擦参数完成物理子步积分。不引入在物理子步注入私有电机电路或串联虚拟齿隙关节的硬件外挂；未来真机适配归入独立的 `real` 类 `Embodiment`。

### 3. 物理端口与 `ObservationSpec` 扩展
- **仿真物理端口补齐本体运动学读取**：在保持每控制节拍单次批量状态同步与单次驱动提交契约不变的前提下，新增刚体线速度与刚体角速度（世界坐标系及机体局部坐标系转换）的确定性读取能力，供动态平衡具身观测与成功判据使用。
- **观测源与动作空间泛化**：向后兼容扩展观测规格契约（既有 `lw.obs-spec/1` 包零修改可读），新增以下通用源与动作空间：
  - `body_angular_velocity`：指定刚体在世界或自身局部坐标系下的三维角速度（单位 `rad/s`）；
  - `projected_gravity`：单位重力方向向量在指定躯干刚体局部坐标系下的三维投影（无量纲单位向量），提供倾斜姿态感知；
  - `command`：由当前执行的 `Device Program` 在每个控制节拍注入的有界一维动作指令向量（服务自定义具身参数化控制、`walkTo` 三维期望机身速度 `[vx, vy, wz]` 以及含参姿态动作等多类消费者），带声明的维度与有限范围校验；
  - `joint_position_offset`（动作空间）：策略网络输出经缩放后叠加在声明的各关节默认参考姿态（`defaultPosition`）之上（可选步进增量限幅）并裁剪至物理关节限位内映射为 `joint_target_q`，同时完整保留既有机械臂使用的 `joint_position_delta` 空间。

### 4. 领域模型：`Waypoint`、通用机器人 `EntityType` 与多动作 `Device Program`
- **场景 `Waypoint` 契约**：在 `Scene` 的定位配置中支持声明命名的地面 `Waypoint`（包含 `Z-up` 地面坐标、期望航向角及可选到达容差半径/角度），供任意移动机器人在跨场景部署时引用；原有面向固定底座机械臂关节角数组的 `Teach Location` 保持完全兼容。
- **双足设备类型与状态暴露**：定义通用双足机器人 `EntityType`（`biped/v1`），声明标准只读状态属性（运行阶段 `phase`、当前执行动作 `activeAction`、躯干是否倾覆 `fallen`、关节位置、当前所在或正前往的 `Waypoint`）以及声明式动作集合（至少包含前往路点 `walkTo`、跌倒恢复 `standUp`、鞠躬致意 `bow` 与并发急停 `stop`，且支持按同一模式扩展更多训练动作）。新增设备类型时同步更新所有依赖全量设备类型清单的静态场景预览，确保预览校验完整可用。
- **多策略动作调度与分层路点导引（遵循 ADR-0008）**：
  - 构建可复用的多策略驱动 `Device Program` 基座：允许在设备绑定配置中声明 `动作名 -> Policy ID` 的映射表（同时兼容单策略绑定与评估覆盖替换模式）。
  - 执行 `walkTo` 时，外层设备程序在每个控制节拍计算机器人当前躯干位姿到目标 `Waypoint` 的局部平面偏差与航向误差，生成平滑限幅的机身期望速度指令向量注入内层 50Hz 行走 `Policy`；进入位置与航向容差圈并稳定驻留后置零速完成动作；若躯干倾角超过安全阈值则立即中止动作、标记 `fallen=true` 并返回结构化失败码（如 `robot_fallen`），引导上层 `Agent` 或操作者调用 `standUp`。
  - 动作参数覆盖检查支持“包络校验（Envelope Coverage）”：对于消费 `command` 向量的含参运动策略，校验注入指令与前置条件是否落在训练任务声明的安全包络内，而非将策略死锁在单一场景的地点名称字符串上。

### 5. 策略评估与 `Controller` 晋升泛化
- 移除策略评估目标描述、候选物校验与 `Controller` 部署核验中仅允许单一机械臂接口的硬编码约束，改为依据场景实际绑定的机器人 `EntityType` 与其注册的策略驱动 `Device Program` 动态校验接口一致性、受控关节子集及单位匹配。
- 在评估会话启动时，当被测对象为某一具体 `Task` 产出的候选 `Policy`（例如测试新训练的 `walkTo` 候选策略），评估器在固定可比较条件下精确替换该机器人在对应动作上的 `Policy` 绑定并统计原生 CPU ONNX 推理调用次数、有效输出次数与观测摘要证据，保持既有评估对比组（Comparison Group）、置信下界接受规则与私密测试集保证不变。
- `Controller` 配置向后兼容扩展以支持记录多动作具身的策略、观测规格、任务与动作空间组合版本；晋升某一动作的新 `Policy` 生成新的 `Controller` 版本并按既有 `Approval Gate` 更新引用。

### 6. 计算节点 MuJoCo Warp（`mjlab` + `rsl_rl`）训练后端（遵循 ADR-0006）
- **任务元数据扩展**：在训练 `Task` Schema 中将后端配置泛化为可判别的后端联合类型：保留既有 `isaaclab` 配置完全兼容，新增 `mjlab` 训练配置（声明训练环境入口标识、并行环境数、控制频率、物理步长、策略网络结构参数及从规范 USD `Asset` 确定性派生的资产映射）。
- **节点执行器与生命周期**：计算节点守护进程根据下发作业的后端类型分派至对应启动器；`mjlab` 启动器在独立 POSIX 进程组中运行 GPU 并行训练，实时采集迭代耗时、步数与 TensorBoard 标量回传网关，支持随时取消并原子清理整个子进程树。
- **标准化 ONNX 导出**：训练完成或保存检查点时，自动将策略网络连同观测经验归一化层一起固化导出为纯前向单输入张量 `.onnx` 文件（无外部动态依赖、兼容平台 CPU `onnxruntime`），并生成对应的 `ObservationSpec` 与导出元数据清单供网关直接注册为 `Policy`。

### 7. Microduck 标杆套件与初始 `Reference` 交付
- 基于上游开源 Microduck 模型（保留其经过验证的连杆几何、质量惯量与平衡站立初始关节角，剥离真机专用电机外挂，完整附带 Apache-2.0 许可证与来源溯源），构建内置规范 `Asset`（14 个受控全身与颈部关节，喙部关节固定或辅助）。
- 交付两个内置或示例 `Scene Version`：
  1. **标准训练与评估场**：空旷平坦地面并布置多方位标准测试 `Waypoint`，绑定对应的 `Evaluation Suite`（覆盖多方向行走到达、随机倒地姿态起身恢复、原地鞠躬致意并恢复站稳三类考核用例）；
  2. **跨场景巡检演示场**：将同一 Microduck `Asset` 置入带实验设备或房间陈设的多实体场景中并配置巡检 `Waypoint`，直观验证零重训跨场景复用。
- 在本机 RTX 3090 GPU 上通过计算节点真实训练产出并通过平台确定性 `Evaluation` 验收首批 3 个轻量 `.onnx` 策略（`walkTo`、`standUp`、`bow`），经人工关口批准作为初始基线 `Reference` 随库内置，使交互会话开箱可动，同时保留完整的 `Task` 定义以便用户或 `Agent` 随时发起新一轮训练。

## Testing Decisions

### 好测试的标准
- **只测系统公开边界上的外部可观测行为，绝不绑定内部私有函数、类名或实现细节**：输入走公开的 HTTP API、CLI、MCP、规范库包与节点心跳协议；断言只看公开返回的响应码、设备状态属性流、三维刚体/站点物理位姿变化、评估报告得分、录制文件完整性与导出的策略包契约。
- **严格区分 GPU-free CI 门禁与本机 GPU/多设备实测**：GitHub CI 全程保持纯 CPU、单任务中位耗时低于 4 分钟；真实大规模并行 GPU 训练与本机 `cuda` 交互仿真作为本地实测验收证据记录，正式记分板 `Evaluation` 保持固定 `cpu` 可比较条件。
- **坚守公共协议与历史录制兼容性**：所有既有协议契约测试、旧版录制回放测试及既有机械臂评估与晋升回归测试必须零退化通过。

### 两条顶层测试接缝（Testing Seams）
1. **接缝 1（主接缝 —— 网关公开 HTTP 动作/评估管线 + 真实 `NewtonSimulation` 闭环）**
   - **通用性防写死验证（自建具身证明）**：在测试夹具中构造一个**全新的最小自定义多关节移动/平衡机器人 `Asset` 与自定义 `EntityType`**（非机械臂、非 Microduck），验证在不改动任何平台代码的前提下，仅通过导入配置即可通过公开 API 完成会话加载、带 `body_angular_velocity` / `projected_gravity` / `command` 的 CPU ONNX 闭环推理控制、`Evaluation Suite` 自动打分以及 `Controller` 晋升全流程。
   - **Microduck 标杆端到端验证**：通过公开会话与动作管线启动标准评估场及跨场景演示场，在真实 `NewtonSimulation`（正式评估与自动化回归走确定性 `cpu`，本机交互仿真验收额外覆盖 `cuda`）下调用 `walkTo`、`standUp`、`bow`、`stop`，验证机器人真实产生受控物理运动到达目标 `Waypoint`、从倒地状态恢复直立、完成鞠躬并正确上报倾覆等异常状态；同时运行公开评估接口验证三个初始 `Reference` 策略达到合格率门槛，且新增设备类型后全部静态场景预览校验保持可用。
   - **仓库既有先例参考**：复用现有真实物理策略评估测试、真实物理端口策略程序测试、控制器晋升事务测试以及静态场景预览完整性测试的公共入口模式。

2. **接缝 2（训练作业接缝 —— 公开训练 HTTP 协议 + 计算节点子进程边界）**
   - **GPU-free CI 契约层**：通过公开的 `Task` 上传、`Training Plan` 创建与人类审批、`Job` 派发及节点心跳接口，配合受控的轻量训练子进程替身与 Schema 校验，验证 `mjlab` 后端任务的准入校验、命令行与环境组装、训练指标与日志流回传、取消时的进程组原子清理，以及 `.onnx` 与 `ObservationSpec` 产物的完整性校验。
   - **本机 RTX 3090 GPU 实训验收层**：启动真实本地网关与计算节点守护进程，在 RTX 3090 上真实运行 `walkTo`、`standUp`、`bow` 三个 MuJoCo Warp + `rsl_rl` 训练 `Job`，验证几分钟内收敛导出 `.onnx`，并将真实产物直接送入**接缝 1** 的平台 `Evaluation Suite` 取得达标分数且训练与平台评估成功率差距在允许阈值之内。
   - **仓库既有先例参考**：复用现有训练作业派发与预算门禁测试、计算节点进程生命周期与 POSIX 进程组清理测试的公共测试模式。

## Out of Scope

- **实体硬件采买与 Sim2Real 真机部署**：本阶段不包含串口舵机通信驱动、`Live Lab` `/Real/` 真机宿主接入、电池压降/齿轮齿隙硬件系统辨识及板端嵌入式部署。
- **手柄/摇杆高频流式遥操作通道**：不在 Web 或网关新增绕过声明式动作管线的实时游戏手柄摇杆流协议；所有控制统一走平台 HTTP 动作管线。
- **视觉导航、SLAM 与复杂三维地形越障**：V1 移动导航聚焦平坦地面上的跨场景 `Waypoint` 巡检与全身动态平衡，不包含机载深度相机渲染训练、激光雷达建图避障或楼梯/崎岖山地跑酷。
- **VLA 视觉语言动作大模型端到端推理与微调**：延续平台既有边界，V1 仅运行轻量强化学习 `.onnx` 策略与设备程序。

## Further Notes

- **运行态与改进态的双层智能分工**：在日常实验与巡检会话（运行态）中，`Agent` 担任高层规划“大脑”，通过 `Operation Plan` 编排 `walkTo`、`standUp` 等声明式动作，而训练所得的 `Policy` 担任高频实时闭环“运动小脑”；在具身研发闭环（改进态）中，`Agent` 担任“科研教练”，基于 `Lab Notebook` 提出可证伪 `Hypothesis` 与 `Training Plan`，经人类在 `Approval Gate` 审批后驱动计算节点与评估中心迭代进化 `Controller`。
- **后续动作与新具身扩展路径**：跑通本规格的通用底座与首批 3 个标杆动作后，无论是为 Microduck 继续扩充翻滚、蹲起、踢球等更多娱乐/实用动作，还是开发者自行建模导入四足机器狗、移动操作臂等全新具身资产，均只需新增相应的 `Asset`、`EntityType`（若为新形态）与 `Task` 包即可直接复用整套流水线。
